## 1. Redis — Impact Analysis

### كل مستهلكي `cacheService` (المسح كامل)

```
server/controllers/storefrontController.js          getOrSetCache ×2  · invalidateCachePattern ×2
server/services/liveActivityService.js              invalidateCachePattern ×4
server/controllers/productsController.js            invalidateCachePattern ×2
server/controllers/productClassificationsController.js  invalidateCachePattern ×3
```

**عمليتا كتابة فقط في المنصة كلها**، وكلتاهما في مسار الواجهة العامة:

| المفتاح | TTL | المحتوى |
|---|---|---|
| `storefront:tenant:<id>:products:<query>` | 120s | نتائج قائمة المنتجات |
| `storefront:tenant:<id>:notifications:<phone>` | 15s | إشعارات العميل |

الباقي كله **إبطال**، لا كتابة. نطاق التأثير صغير — لكن حافته حادة.

### ما الذي يتغير سلوكيًا إذا اتصل Redis فعلًا

| البُعد | اليوم (ذاكرة) | بعد Redis | الحكم |
|---|---|---|---|
| **TTL** | `expiresAt` محلي | `EX` | متطابق |
| **البقاء بعد إعادة التشغيل** | يُمسح | **يبقى** | 🟠 نشرة جديدة قد تخدم payload من الكود القديم حتى 120 ثانية. المفتاح لا يحوي رقم البناء |
| **Serialization** | يخزّن **نفس المرجع** | `JSON.stringify/parse` | ✅ غير مرئي هنا: كلا الـpayloadين يذهبان مباشرة إلى `res.json`، فالتحويل يحدث أصلًا. **لكنه فخ لأي مستهلك مستقبلي**: أعمدة `timestamp` تعود من pg كـ`Date`، وتصبح نصًا بعد Redis |
| **Aliasing** | مرجع مشترك — طلب يعدّله يفسده للبقية | نسخة جديدة كل مرة | ✅ Redis **يصلح** خللًا كامنًا |
| **الإبطال** | regex محلي، فوري | `SCAN` + `DEL` | 🟠 غير ذرّي، وقد يفوت مفاتيح تُكتب أثناء المسح |
| **عدة replicas** | كل نسخة لها cache خاص؛ الإبطال لا يعبر بينها ⇒ **بيانات قديمة حتى انتهاء TTL** | cache واحد، إبطال عالمي | ✅ Redis **يصلح** خللًا حقيقيًا قائمًا |
| **Thundering herd** | لا single-flight | كما هو | ⚪ لا يسوء |

### 🔴 خطر ملموس واحد

[productsController.js:48](../../server/controllers/productsController.js)

```js
const invalidateProductStorefrontCache = async (tenantId) => {
  await Promise.all(... invalidateCachePattern(...) ...);   // بلا catch
};
```

اليوم لا يمكن أن يرمي: `getRedisClient()` يعيد null والمسار الذاكري لا يفشل. **بعد تفعيل Redis**، فشل `scanIterator` يتصاعد — و**حفظ منتج قد يفشل لأن إبطال الـcache فشل**. الثلاثة الأخرى محروسة بـ`.catch`؛ هذا ليس.

### 🔴 إعداد Redis الحالي مضبوط لقاعدة بيانات، لا لـcache

من فحص الإنتاج:

```
maxmemory         0            ← بلا حد
maxmemory-policy  noeviction   ← عند الامتلاء: الكتابة تفشل بدل الإخلاء
appendonly        yes          ← يكتب على قرص ممتلئ 74%
save              3600 1 300 100 60 10000
requirepass       (غير مضبوط)  ← داخل شبكة docker مع 5 حاويات، غير مكشوف للإنترنت
```

**`noeviction` هو عكس ما يريده الـcache** (يريد `allkeys-lru`)، و**الـAOF تضخيم كتابة لا يحتاجه الـcache** على قرص عند 74%.

لكن **هذا الإعداد بالضبط هو الصحيح لعدّادات rate limit**: صغيرة، لها TTL، وفقدانها غير مرغوب. الإعداد مناسب لاستخدامي وغير مناسب للاستخدام الآخر.

### التوصية

> **Shared explicit Redis infrastructure** — وحدة اتصال واحدة صريحة، يستخدمها Surveillance فورًا، ويبقى `cacheService` عليها **خلف علم مُطفأ**.

| البديل | لماذا لا |
|---|---|
| `cacheService` الحالي | تفعيله يغيّر مسار الواجهة العامة الساخن، ويكشف الخلل أعلاه، ويشغّل cache على Redis مضبوط كقاعدة بيانات — كل ذلك كأثر جانبي لميزة كاميرات |
| عميل Redis مخصّص للمراقبة | يحل المشكلة لكنه يفتح اتصالًا ثانيًا لنفس الخادم ويكرّر منطق إعادة الاتصال والفشل. أنظف من الأول، وأسوأ من الثالث |
| **بنية Redis مشتركة صريحة** | ✅ اتصال واحد · Surveillance يستفيد فورًا · قرار الـcaching يبقى منفصلًا ويُختبر وحده لاحقًا |

**السبب الجوهري**: العدّادات والـcache صنفان مختلفان من البيانات بسلوك فشل مختلف. فقدان cache = بطء. فقدان عدّاد = ضابط أمني متدهور. دمجهما خلف مفتاح واحد يعني أن قرارًا عن الأداء يحرّك ضابطًا أمنيًا، والعكس.

**قبل تفعيل الـcaching لاحقًا** (منفصلًا): ضع `maxmemory` و`allkeys-lru`، أطفئ الـAOF أو افصل قاعدة بيانات، احرس `invalidateProductStorefrontCache`، وأضف رقم البناء إلى مفتاح الـcache.

**لم أضف أي dependency ولم ألمس `package.json`.**

## 2. SSRF — نطاق `172.16.0.0/12`

### الاعتراض صحيح

منع `172.16.0.0/12` عالميًا يمنع شبكات عملاء حقيقية (`172.16.x`، `172.20.x`). الهدف المعلن هو **منع بنية مضيف الـERP**، لا منع نطاق RFC1918 كاملًا للأبد.

### هل توجد ثغرة فعلية الآن؟ **لا**

الطبقة 2 (قراءة واجهات المضيف وقت التشغيل) تغطي كل جسور Docker الثمانية الفعلية بالفعل، وهي **غير قابلة للاستثناء**. الطبقة 1 (`/12`) هي حزام فوق حمّالة: تغطي جسرًا قد يُنشأ بين قراءتين متتاليتين للواجهات (نافذة 30 ثانية).

فلا تغيير عاجلًا. لكن الافتراضي أوسع من اللازم للمستقبل.

### التحسين المقترح (لـ2B-1، لا الآن)

**اجعل الطبقة 1 تُطفئ نفسها حين لا تنطبق:**

```
هل لهذا المضيف واجهة داخل 172.16.0.0/12؟
  نعم ⇒ إنه مضيف حاويات يخصّص من هذا النطاق. فعّل منع الـpool.
  لا  ⇒ لا شيء هنا ملكنا. لا تمنع النطاق إطلاقًا.
```

النتيجة:

| النشر | له واجهات 172.16/12؟ | سلوك الطبقة 1 |
|---|---|---|
| VPS الحالي | نعم (ثمانية جسور) | مفعّلة — كما اليوم |
| Edge Agent على شبكة عميل | لا | **مطفأة** — شبكة `172.20.x` للعميل تعمل بلا أي إعداد |
| Self-hosted بلا Docker | لا | مطفأة |
| Self-hosted بـDocker | نعم | مفعّلة، والاستثناء المحروس متاح |

هذا يطابق الهدف حرفيًا: **يُمنع ما نملكه فعلًا، لا ما يشبهه.** والـ`SURVEILLANCE_INFRA_EXEMPT_CIDRS` يبقى للحالة المختلطة الأخيرة.

### لماذا يجعل الـEdge Agent الفصل أنظف

القاعدتان مختلفتان جوهريًا لأنهما تحرسان شيئين مختلفين:

| | Cloud (الـERP) | Agent (داخل المحل) |
|---|---|---|
| ما الذي يحرسه | بنيتنا نحن من مدخلات العميل | شبكة العميل من أوامرنا نحن |
| النموذج | **hard deny** لكل ما نملكه | **allowlist صريح** لأجهزة وافق عليها المالك |
| الوجهات | **الوكلاء المسجّلون فقط** عبر mTLS | عناوين LAN محلية |
| Topology | `cloud` | `lan` |
| `172.16/12` | مفعّل (مضيف حاويات) | **غير ذي صلة** |

**الملاحظة الأهم**: بمجرد وجود الـagents، الـERP **لا يتصل بشبكة أي عميل إطلاقًا**. سطح الـSSRF لديه ينكمش إلى قائمة ثابتة صغيرة من الوكلاء — وسؤال `172.16/12` يختفي من جانب السحابة تمامًا. أما الوكيل فلا يواجه سؤال SSRF أصلًا: ليس لديه مستخدم يُدخل عنوانًا، بل قائمة أجهزة اعتمدها المالك.

المعمارية الحالية تدعم الاثنين بالفعل عبر `SURVEILLANCE_HOST_TOPOLOGY` وترتيب الطبقات. التحسين أعلاه يزيل آخر افتراض سحابي من الافتراضي.

**القرار: توثيق الآن، تنفيذ في 2B-1، لا تغيير عاجل — لعدم وجود ثغرة فعلية.**
